# Перенос на внешний сервер и интеграция с 1С

## 1. Можно ли перенести проект на сервер отдела ИТ

**Да.** Проект не привязан к Vercel: это обычное Next.js-приложение с PostgreSQL. Vercel/Neon можно оставить как staging, а production поднять на Linux-сервере.

### Что переносится

- Next.js 15 (App Router, SSR/SSG, API routes);
- PostgreSQL 16 (вместо локальной PGlite);
- Drizzle-миграции и seed;
- файлы изображений (лучше в S3/MinIO, не в контейнер);
- фоновые задачи синхронизации с 1С (worker);
- TLS, домен, почта, SMS, ЮKassa, аналитика.

### Сложность

| Работа | Сложность | Срок |
|---|---|---|
| Подготовка VM, DNS, TLS, firewall | низкая | 0,5–1 день |
| Docker-образ, compose, Postgres, миграции | низкая | 1–2 дня |
| Перенос данных и медиа | низкая | 0,5–1 день |
| CI/CD, бэкапы, мониторинг | средняя | 1–2 дня |
| Приёмка, нагрузка, переключение DNS | средняя | 1–2 дня |
| **Итого без 1С** | **средняя** | **3–7 дней** |

Основной риск — не код, а согласование доступа, сеть до 1С, бэкапы и эксплуатация.

### Рекомендуемая архитектура

```
Интернет
   │
Caddy / Nginx (TLS, rate limit, HSTS)
   │
Next.js app :3000  ──────► PostgreSQL 16
   │                         │
   ├── worker (sync/outbox) ─┘
   ├── Redis (queue/cache, опционально)
   ├── MinIO/S3 (изображения)
   └──── VPN/private network ───► 1С HTTP-сервис
```

Для старта достаточно **одной VM**:

- Ubuntu 22.04/24.04 LTS;
- 4 vCPU, 8 ГБ RAM, 80–100 ГБ SSD;
- Docker + Compose;
- Caddy (автоматический Let's Encrypt);
- PostgreSQL в контейнере или managed;
- отдельный том/бэкап для БД и медиа.

1С лучше держать **на отдельном сервере**, не на этой же VM.

### Docker

В репозитории уже есть `Dockerfile` (multi-stage, standalone Next.js) и `docker-compose.yml`. Для production нужен отдельный compose/override:

- пароль Postgres — из секрета, не `irbis_dev_password`;
- `DEMO_PAYMENTS=false`;
- `AUTH_SECRET` — уникальный;
- том `pgdata` и регулярный `pg_dump`;
- Caddy с доменом;
- worker как отдельный сервис;
- healthcheck `/api/health`;
- non-root пользователь;
- `restart: unless-stopped`.

### Перенос данных с текущего Vercel/Neon

1. `pg_dump` из Neon → `pg_restore` в новый Postgres.
2. Проверить миграции (`drizzle-kit migrate`), количество товаров/заказов.
3. Перенести изображения из `public/images` в S3/MinIO, обновить URL.
4. Прописать env: `DATABASE_URL`, `AUTH_SECRET`, `NEXT_PUBLIC_SITE_URL`, ЮKassa, SMTP, SMS, 1С.
5. Прогнать smoke: главная, каталог, вход, заказ, оплата, админка.
6. Переключить DNS с TTL 300, оставить Vercel для отката.

### Эксплуатация

- **Бэкапы:** ежедневный `pg_dump` + media, хранение 30 дней, тест восстановления раз в месяц.
- **Мониторинг:** Uptime Kuma/Prometheus, Sentry, алерты на 5xx, очередь, диск, БД.
- **Безопасность:** SSH-ключи, firewall, fail2ban, обновления, non-root контейнеры, секреты вне git.
- **152-ФЗ:** сервер и 1С в РФ, согласия на обработку ПД, политика, журналы доступа.
- **PCI DSS:** карты не хранить, использовать hosted-страницу ЮKassa.
- **Отказоустойчивость:** одна VM — точка отказа; для production позже managed Postgres + реплика + второй app-контейнер.

### Если ИТ даст Windows-сервер

Лучше попросить Linux VM. Если только Windows — Docker Desktop/WSL2 либо IIS как reverse proxy к Linux-контейнеру; это менее удобно для эксплуатации.

## 2. Интеграция с 1С

**Да, полноценная интеграция возможна.** Нужен не прямой доступ к базе 1С, а сервисный контур: 1С отдаёт/принимает данные по HTTP, сайт хранит очередь и повторяет операции.

### Варианты

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **HTTP-сервис 1С (REST/JSON)** —推荐 | 1С публикует `/hs/site/v1/...`, сайт вызывает |实时, контроль, idempotency, статусы | Нужна доработка 1С и публикация HTTP |
| **CommerceML / XML-обмен** | 1С выгружает XML, сайт импортирует | Стандарт для каталога/цен/заказов, знаком 1С-никам | Не real-time, файлы, сложнее статусы |
| **OData** | Сайт читает справочники | Быстрый read-only старт | Слабые записи, производительность, безопасность |
| **Прямое подключение к БД 1С** | SQL к таблицам | «Быстро» | **Не рекомендуется:** блокировки, хрупкость, обновления 1С, безопасность |
| **Очередь/шина (RabbitMQ/Kafka)** | События между системами | Масштаб, развязка | Избыточно для старта |

**Рекомендация:** HTTP-сервис 1С + очередь/outbox на сайте. Если 1С-команда не может сделать HTTP — начать с CommerceML для каталога/цен, а заказы — через HTTP или файловый обмен.

### Кто master данных

| Данные | Master | Комментарий |
|---|---|---|
| Номенклатура, штрихкоды, единицы, НДС | 1С | сайт хранит `externalId` (GUID) |
| Цены, скидки, акции 1С | 1С | сайт применяет свои промокоды отдельно |
| Остатки, резервы, склады | 1С | сайт кэширует + резервирует при заказе |
| Описания, фото, SEO, баннеры | сайт | контент-слой поверх 1С |
| Клиенты, согласия, бонусы | сайт | 1С — контрагент по GUID |
| Заказы | сайт создаёт, 1С обрабатывает | статусы из 1С |
| Оплата | ЮKassa + сайт | фискализация в 1С/ОФД |
| Отзывы, рейтинги | сайт | не из 1С |

Главное правило: **у каждого поля один master**, иначе конфликты и «перетирание» данных.

### Контракт (пример)

Сайт → 1С:

```http
POST /hs/site/v1/orders
Authorization: Bearer <service-token>
Idempotency-Key: <order-uuid>

{
  "orderId": "uuid",
  "number": "IM-2026-000107",
  "customer": { "name": "...", "phone": "...", "email": "..." },
  "delivery": { "type": "PICKUP", "storeId": "..." },
  "items": [{ "externalId": "1c-guid", "sku": "...", "qty": 2, "price": 890 }],
  "total": 1780,
  "payment": { "method": "ONLINE", "status": "PAID" }
}
```

1С → сайт:

```http
POST /api/integration/1c/catalog
X-Signature: sha256=<hmac>
X-Timestamp: 1760000000

{ "items": [{ "externalId": "guid", "name": "...", "price": 890, "stock": 12 }] }
```

Минимальный набор endpoints:

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | `/hs/site/v1/orders` | создать заказ, зарезервировать |
| POST | `/hs/site/v1/orders/{id}/cancel` | отмена, снятие резерва |
| GET | `/hs/site/v1/orders/{id}` | статус, номер 1С |
| POST | `/hs/site/v1/stock/reserve` | резерв по складу |
| POST | `/hs/site/v1/stock/release` | снять резерв |
| POST | `/api/integration/1c/catalog` | full/delta каталога |
| POST | `/api/integration/1c/prices` | цены и скидки |
| POST | `/api/integration/1c/stocks` | остатки |
| POST | `/api/integration/1c/orders/status` | webhook статусов |
| POST | `/api/integration/1c/counterparties` | контрагенты (опционально) |

Требования к контракту:

- идемпотентность по `externalId`/`orderId`;
- `changedSince`/`updatedAt` для delta;
- пагинация и batch;
- HMAC-подпись + timestamp + IP allowlist;
- таймауты, retry с backoff, dead-letter;
- журнал `integration_events` и ручной replay;
- сверка (reconciliation) раз в сутки.

### Каталог

1С отдаёт: GUID, артикул, штрихкод, название, категорию, цену, НДС, единицу, вес/фасовку, остаток, склад, изображения, свойства, статус.

Сайт:

- upsert по `externalId`, slug генерируется и не меняется;
- удалённые товары — `archived`, не hard delete;
- контентные поля (описание, фото, SEO) хранятся отдельно и не перетираются 1С;
- изображения — в S3/MinIO + CDN, fallback;
- категории маппятся по GUID, а не по названию.

### Остатки и резервы

Для супермаркета остатки меняются быстро. Варианты:

1. **Кэш + резерв в 1С при checkout** (рекомендуется): сайт показывает остаток с лагом 1–5 мин, при заказе вызывает резерв; если не удалось — 409 и предложение замены.
2. **Только кэш + буфер**: сайт держит safety stock, 1С синхронизирует раз в N минут; риск oversell.
3. **Real-time запрос в 1С на каждую карточку** — плохо для производительности; не делать.

Нужны:

- остатки по складам (магазин, dark store, самовывоз);
- резерв с TTL (например, 15–30 мин до оплаты);
- снятие резерва при отмене/истечении;
- сверка «сайт vs 1С» и алерты.

### Заказы и статусы

- сайт создаёт заказ в своей БД + outbox-событие в одной транзакции;
- worker отправляет в 1С, получает номер и статус;
- статусы 1С → webhook → сайт (маппинг: `NEW`, `PROCESSING`, `READY`, `DELIVERING`, `COMPLETED`, `CANCELED`);
- если 1С недоступна, заказ принимается со статусом «ожидает подтверждения», retry;
- оплата и фискализация: ЮKassa — деньги, 1С/ОФД — чек; не дублировать;
- возвраты: документ возврата в 1С + refund в ЮKassa.

### Клиенты и лояльность

- гость может оформить заказ; аккаунт — опционально;
- 1С-контрагент создаётся/сопоставляется по GUID;
- бонусы — лучше оставить на сайте (простая логика, история, маркетинг);
- в 1С передавать сумму скидки/бонусов, чтобы чек был корректным;
- 152-ФЗ: согласие, минимизация, сроки хранения.

### Промо и цены

- цены 1С — база; сайт может иметь промо-цены и промокоды;
- правило стекирования: сначала цена 1С, затем промокод, затем бонусы; либо запрет суммирования;
- округление и копейки — фиксированные правила;
- не редактировать цену в 1С и на сайте одновременно.

## 3. Этапы внедрения

| Этап | Результат | Срок |
|---|---|---|
| 0. Аудит 1С | версия, HTTP-сервисы, склады, цены, статусы, тестовый контур | 2–3 дня |
| 1. Инфраструктура | VM, Docker, Postgres, TLS, бэкапы, staging | 3–7 дней |
| 2. Каталог | импорт номенклатуры, категорий, цен, фото | 1–2 недели |
| 3. Остатки | sync + резервы + сверка | 1–2 недели |
| 4. Заказы | создание, статусы, отмена, уведомления | 2–3 недели |
| 5. Оплата/фискализация | ЮKassa, чеки, возвраты | 1–2 недели |
| 6. Приёмка | нагрузка, сбои, безопасность, обучение | 1–2 недели |

Ориентир: **MVP 4–6 недель**, полноценный контур **8–12 недель** при выделенной 1С-команде. Если у 1С уже есть готовый HTTP-сервис/CommerceML — быстрее.

## 4. Что запросить у ИТ и 1С

**У ИТ:**

- Linux VM (Ubuntu), 4 vCPU/8 GB/100 GB SSD;
- внешний IP, DNS, TLS-сертификат или Let's Encrypt;
- доступ по SSH/VPN, firewall;
- SMTP-relay, S3/MinIO или бакет;
- бэкапы и мониторинг;
- тестовый и production контуры.

**У 1С:**

- конфигурация и версия (УТ 11.5, ERP 2.5, УНФ 3.0, 7.7?);
- опубликованные HTTP-сервисы или готовность их сделать;
- тестовая база;
- справочники: номенклатура, склады, цены, контрагенты;
- статусы заказов и правила резерва;
- доступ к документации API.

## 5. Главные риски

1. **Нет HTTP-сервиса в 1С** → придётся делать обмен файлами/CommerceML, срок растёт.
2. **Остатки не резервируются** → oversell и ручные разборы.
3. **Двойной master цен** → конфликты и неверные чеки.
4. **1С недоступна** → заказы должны приниматься в очередь, а не падать.
5. **Одна VM** → SPOF; нужны бэкапы и план восстановления.
6. **152-ФЗ/PCI** → хостинг в РФ, hosted-оплата, минимизация ПД.

## 6. Итог

- Перенос на сервер — **реалистично за 3–7 дней**, код переписывать не нужно; основной объём — инфраструктура и приёмка.
- Интеграция с 1С — **реалистично за 4–12 недель** в зависимости от готовности 1С; делать через HTTP-сервис + outbox/queue, без прямого доступа к БД 1С.
- Полноценный магазин = каталог + цены + остатки/резервы + заказы/статусы + оплата/чеки + клиенты/лояльность + сверка.

## 7. Сайт и приложение — одна система

Мобильное приложение не является отдельным бэкендом. Это ещё один клиент к тому же сайту/API:

```
Сайт (Next.js, SSR) ─┐
Админка (web) ───────┼──► API + PostgreSQL ──► 1С-адаптер ──► 1С
Мобильное приложение ┘         │
                               ├── S3/MinIO (изображения)
                               └── worker (очередь, синхронизация)
```

### Что переносится на сервер

1. **Сайт**: витрина, каталог, карточки, корзина, checkout, акции, кафе, контакты, SEO.
2. **Личный кабинет**: вход, заказы, бонусы, адреса, профиль.
3. **Админка**: товары, категории, заказы, промокоды, пользователи, CSV.
4. **API**: auth, products, orders, payments, bonuses, admin.
5. **PostgreSQL** и миграции.
6. **Медиа** (S3/MinIO + CDN).
7. **1С-интеграция**: один адаптер, один worker, одна очередь.
8. **Инфраструктура**: TLS, бэкапы, мониторинг, cron.

### Что меняется в приложении

- Если APK — Capacitor-обёртка, он открывает URL сайта. При переезде:
  - сохраняем **тот же публичный домен** → APK продолжает работать без пересборки;
  - меняем домен → нужен новый APK с новым `server.url` и `allowNavigation`.
- Если позже делать React Native/Expo — приложение использует те же API, без отдельной интеграции с 1С.
- Push-уведомления, deep links и биометрия — только в мобильном клиенте, но данные и заказы общие.

### Правильная стратегия домена

Лучше сразу закрепить **стабильный домен компании**, например `mart.irbis.ru`, и не использовать `*.vercel.app` в APK.

Тогда:

1. Сейчас домен указывает на Vercel.
2. При переезде меняется только DNS/прокси на сервер ИТ.
3. Сайт и приложение продолжают работать по тому же адресу.
4. APK не нужно пересобирать.

Если домена пока нет — при переезде придётся выпустить новую версию APK.

### Порядок переезда сайта и приложения

| Шаг | Сайт | Приложение |
|---|---|---|
| 1. Сервер и БД | staging-домен, миграции | пока работает старая версия |
| 2. 1С test | каталог/остатки/заказы | использует тот же API |
| 3. Production cutover | DNS → сервер, 301, SSL | старый APK работает, если домен сохранён |
| 4. Если домен новый | обновить canonical/sitemap/OG | выпустить APK с новым URL |
| 5. Проверка | SEO, оплата, почта, вебхуки | вход, заказ, оплата, push |

### Важно для SEO при переезде

- сохранить URL-структуру;
- настроить 301 со старых адресов;
- обновить `canonical`, `sitemap.xml`, `robots.txt`, OG;
- добавить новый домен в Яндекс.Вебмастер и Google Search Console;
- проверить HTTPS, HSTS, редиректы с `www`;
- сохранить аналитику и цели.

### Итог

- Переносим **весь проект**: сайт, кабинет, админку, API, БД, медиа и 1С-интеграцию.
- Приложение — клиент; отдельный бэкенд и отдельная интеграция с 1С ему не нужны.
- Один 1С-адаптер обслуживает и сайт, и приложение.
- Чтобы не перевыпускать APK при переезде, нужен стабильный домен компании.
